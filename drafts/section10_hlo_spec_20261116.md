That variable is read only by `harness/af3_entry.py`, in a block added for this follow-up (additive; without the variable nothing in it runs and `XLA_FLAGS` is untouched, so every earlier configuration runs as before): before AlphaFold 3 and JAX are imported, it sets `XLA_FLAGS` to `--xla_dump_to=<process folder>/xla_dump` followed by the variable's flags (`tpu_xla` sets no `XLA_FLAGS`), because XLA reads `XLA_FLAGS` once, when the backend starts, and because each process needs its own dump folder: every AlphaFold 3 process of a session runs in the same working directory and XLA names dump files by a module number that repeats from process to process, so a fixed `--xla_dump_to` in the configuration would let the processes overwrite each other's dumps. XLA then writes, per process, the model's module as text before (`module_*.jit_apply_fn.before_optimizations.txt`) and after its optimisations (`module_*.jit_apply_fn.*after_optimizations.txt`, with companion files such as the buffer assignment), each instruction with its `op_name` (the Haiku module path, for example `diffuser/evoformer/__layer_stack_no_per_layer/trunk_pairformer/...`) and a stack frame resolved by the tables at the head of the file (source file, function and line). What is set is recorded per process in `af3_entry_stats.json` (`hlo_dump`: the flags, the number and size of the files, the optimised module's file name). Why the dump does not change the compilation: XLA's dump options are debug options that write files and set no compiler pass; JAX leaves them out of its persistent-cache key because they "do not affect the compile result" (`jax/_src/cache_key.py`, jax 0.10.2, `xla_flags_to_exclude_from_cache_key` and `_hash_serialized_compile_options`); the harness gives every process a fresh, empty compile cache, so every process compiles.
